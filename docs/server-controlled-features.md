# Что меняется с сервера, а что требует новой сборки

Состояние 22.11.2026, версия 1.0.2. Код API — `/Users/amanyessen/projects/flyprox_backend/src/server.js`; прод — `/home/myuser/projects/flyprox_backend`, systemd user-сервис `flyprox-backend`, публичный адрес `https://api.flyprox.com`. Это Node.js Express, работающий постоянно на сервере. Appwrite хранит таблицы, аккаунты и push targets; отправка идёт через Messaging. Appwrite Functions сейчас не используются и для изменения текущих правил не нужны.

## Вопросы — серверный источник

Редактируемый банк находится в Appwrite, база maindb, таблица `questions`. Вопрос содержит `seedId`, `textEn`, `textRu`, `category` (sympathy/normal/humor), `emoji`, `isIntro`. Приложение сейчас английское: русская клавиатура язык не переключает. Автолокализацию пользователь отложил.

Публичный `GET /api/questions?limit=250&cursor=<id>` отдаёт только тексты и метаданные вопросов, без профилей. `nextCursor=null` завершает загрузку. Приложение обновляет банк в фоне при запуске и сохраняет только целиком полученный валидный результат. Гостю не нужен вход для получения вопросов. Без сети используется последний загруженный банк; при первой установке совсем без сети — встроенный резерв. Это страховка офлайна, а не второй редактируемый источник.

Лимит первых 500 убран и для серверных раундов. Постраничность проверена на 10000 вопросах, без записи 10000 фиктивных строк на прод. Новые вопросы можно добавлять в таблицу без обновления iOS; нужно дождаться полной загрузки банка приложением. Держать минимум четыре основных вопроса в каждой категории. `isIntro=true` — вводные вопросы, false — основной банк. Не удалять активные вопросы во время раундов без отдельного механизма версий; лучше готовить новую ревизию.

Один раунд всё ещё 12 вопросов, четыре в категории. Количество карточек, минимум четыре друга и 40 минут ожидания зафиксированы также в клиенте. Менять их только на сервере нельзя: сначала требуется согласованная клиентская поддержка.

Для массового добавления есть CLI в backend:

```bash
npm run questions:import -- /path/questions.json
npm run questions:import -- /path/questions.json --apply
```

Первая команда только валидирует, без API-записи и без необходимости ключей. Вторая импортирует, пропуская уже существующие seedId; `--update-existing` явно разрешает обновить их. Повтор после обрыва безопасен по стабильным seedId. Пример одной записи:

```json
{"seedId":"custom_001","textEn":"Who always cheers you up?","textRu":"Кто всегда поднимает настроение?","category":"sympathy","emoji":"⭐","isIntro":false}
```

Файл — JSON-массив таких объектов. До первой записи проверяется весь файл: уникальные seedId до 64 символов, оба текста до 512, emoji до 16, допустимые category и boolean isIntro. Импорт выполняется последовательно и может занять время для 10000 записей; сначала dry-run и резервная копия банка. Никогда не добавлять credentials в этот JSON.

## Тексты и флаги без деплоя

Консоль Appwrite → project flyprox → Databases → maindb → `content_items` (в UI может отображаться ContentItems). Менять `value` у существующего `key`. Публичный endpoint: `/api/content`.

| Ключи | Формат и назначение |
|---|---|
| `invite_message` | Текст приглашения |
| `paywall_title`, `paywall_subtitle`, `paywall_product_name`, `paywall_term`, `paywall_cta` | Заголовки/подписи пейвола; не менять ими реальную цену Apple |
| `paywall_features` | JSON-массив преимуществ |
| `upsell_timer_button`, `upsell_reveal_note` | Подписи предложений Premium |
| `blocked_title`, `blocked_body` | Legacy-текст; новый глобальный экран ограничения использует фиксированную копию в коде |
| `onboarding_pages` | JSON-массив объектов: `emoji`, `title`, `subtitle` |
| `url_support`, `url_terms`, `url_privacy`, `url_marketing`, `support_email` | Публичные ссылки и support email |
| `guest_enabled`, `contacts_enabled` | Строка `true` или `false`, показ соответствующих элементов |
| `example_names_enabled` | `false` скрывает кнопку примеров вместе с пояснением (начиная со следующей сборки после 9) |
| `example_names_button` | Надпись кнопки примеров |
| `example_names_description` | Пояснение рядом с кнопкой примеров |

Кэш текстов — 12 часов; обновление происходит в фоне при запуске. Ошибка сервера/невалидное значение возвращает зашитый дефолт. Не обещать мгновенную смену экрана у уже открытого приложения. `guest_enabled` скрывает гостевую кнопку на телефоне, но не является глобальным запретом гостевой игры: примеры/офлайн остаются. `contacts_enabled` управляет кнопкой, а не правами iOS и не стирает уже выбранные имена.

Юридические строки автопродления намеренно остаются в коде. Цена/валюта покупки берётся из StoreKit и товара Apple, а не из произвольного текста в таблице.

## Пуши без выпуска iOS

Правила живут в backend `POST /api/votes`, текст — `buildVotePush()` в `src/rules.js`. Сейчас: первое голосование одного пользователя за другого в раунде → попытка push. Не отправлять при skip, локальном несовпавшем имени и голосе за себя. Получатель должен быть в совпавших выбранных контактах; произвольный account ID не даёт права отправить ему голос.

Условия, текст и ограничение частоты можно менять новым деплоем backend без iOS-сборки, пока используется уже поддерживаемый тип уведомления. Для переноса текстов push в таблицу/расписания сначала добавить соответствующую серверную поддержку: обычная правка `content_items` сейчас текст `buildVotePush()` не меняет.

Доставка: backend → Appwrite Messaging → APNs → устройство. Нужны production provider, device target и разрешение. Backend не может сам разрешить уведомления на телефоне. Новые интерактивные действия, обработка deep link, фоновая логика или новый permission потребуют клиентского кода.

Рекомендации для следующих этапов: очередь/outbox с повторами, idempotency key, лимиты на получателя и отправителя, тихие часы с часовым поясом, возможность отключить тип уведомлений, логи статусов без токенов/номеров. Не выдавать эти планы за уже реализованные функции.

## Другие настройки

| Что | Где менять | Новая iOS-сборка |
|---|---|---|
| Разрешённые SMS-страны/тестовые номера | Firebase Identity Toolkit configuration; сейчас US,GB,CA,NZ,SG,HK; тест +16505551234/123456 | Нет |
| SMS-проверка, серверные проверки/лимиты, подбор вопросов, matching | Код Node API + тесты + деплой | Обычно нет, если контракт прежний |
| APNs ключ/production provider | Appwrite Messaging | Нет при прежнем bundle/topic |
| Системный текст разрешения, callback URL scheme, capability, новый SDK | iOS/Flutter | Да |
| Расположение кнопок, экран контактов, клавиатура, новые экраны | Flutter/native UI | Да |
| Стоимость/доступность подписки | App Store Connect и настройки продукта Superwall | Зависит от изменения продукта/клиентского контракта; строкой текста цену не заменить |
| Terms/Privacy/Support | Публичные Notion-страницы | Нет для текста страниц, но practices/labels должны совпадать с выпускаемой версией |
| App Privacy labels | App Store Connect веб-анкета | Само редактирование без бинарника; публиковать согласованно с версией |

Нельзя загрузкой серверного исполняемого кода тайно превращать приложение в другой продукт. Content/config предназначены для поддерживаемого поведения, а существенные новые возможности требуют обычного выпуска и честного описания.

## Что удобно вынести дальше

1. Версии банка вопросов, staged публикация, архивирование вместо удаления и резервные копии. Для 10000 строк нужен импорт с валидацией, стабильными ID и проверкой дублей; не добавлять их вручную по одной.
2. Push-шаблоны и частоты, с разумными значениями по умолчанию, audit trail и отменой изменений.
3. Контент по языкам с явным выбором языка; не определять его по клавиатуре. Сейчас язык не меняем.
4. Минимальная поддерживаемая версия, сообщения об обслуживании, мягкое отключение online при сбое. Клиент должен заранее поддержать эти флаги; их ещё нет.
5. Админ-предпросмотр и валидатор JSON для текстов; не позволять таблицей менять purchase legal copy или charge amount.
6. Надёжное удаление аккаунта и данных провайдеров, полный обход всех страниц данных и подтверждение результата. Сейчас это известный пробел перед публичным App Store review.
